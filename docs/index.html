Quickstart

Three commands to a running console.

The development stack runs in mock mode: the full flow, with no real target infrastructure. It needs Docker with Compose v2.

install and launch
$ git clone https://github.com/gianlucabassani/Nidavellir.git
$ cd Nidavellir
$ make dev
  1. Open localhost:5000 for the console. The API is on localhost:8000.
  2. Sign in with the demo login, admin / nidavellir.
  3. Stop everything with make dev-down.

Run it on a machine you control. The demo credentials are public and the stack holds the Docker socket, so never expose it. For real Docker-local arenas read the Operations guide; for production, the Deployment guide.

I · The run

From a pinned target to a verdict that holds.

The same five stages serve a human researcher and an agent under evaluation.

  2. i.

    Pin a target

    Import a Git repo, OCI image or source bundle. The exact version under test is recorded.

  3. ii.

    Launch an arena

    An isolated N-node Docker topology with bounded resources and a reset path.

  4. iii.

    Work, scoped

    The agent connects over MCP with tools bound to one arena and a durable budget.

  5. iv.

    Referee the claim

    Deterministic validators re-check the finding against the target, not the agent's word.

  6. v.

    Keep the evidence

    Transactions, traces and events outlive the arena; scores derive from the event log.

IV · Architecture

Thin clients, one authority.

All authorization lives in the orchestrator API. The console and the MCP gateway are scoped clients of it, and only the worker side touches Docker.

Swipe the diagram sideways to see all of it →

One place decides

The console and the gateway hold no authority of their own. Every request is authorized by the API, which also owns validation and scoring.

The gateway is optional

It starts only with the agent-gateway profile, and an agent key must be bound to an arena and a stance before any tool call is accepted.

Docker is the trust boundary

The orchestrator and the worker mount the Docker socket, which is root-equivalent on the host. Use a dedicated host or VM.

V · Development roadmap

What is forged, what is on the anvil.

Claims are limited to what has live acceptance records in the repository. Correctness, containment and independent verification come before feature count.

Shipped

Verified on Docker-local

Each item has a live acceptance run recorded in the repository.

  • Research runtimePinned release gate, arena lifecycle and reset, confined PoC execution, durable budgets and stop, scoped access.
  • Verified resultsIndependent validation, durable paired trials, calibration challenges, a bring-your-own-agent workflow, record recovery.
  • Affected-versus-fixed replayThe same request replayed against a vulnerable and a fixed version of a target.
  • Operator consoleEvidence review, request comparison and source-candidate review.
  • Fail-closed defaultsInsecure configuration is refused outside mock mode; login throttling, session and CSP headers, bounded arena containers.

On the anvil

Target-led next steps

Each starts when a concrete research target and suitable evidence justify it.

  • Fuzzing and crash triageAutomated fuzzing behind an accepted service contract.
  • Local VM intakeBinary, appliance and VM targets through a local hypervisor.
  • Research campaignsFindings across versions, deduplication and disclosure output.
  • Held-out evaluationPrivate challenges, so a score can say something about capability.

Deferred

Not before there is a need

None of these block the single-team, self-hosted product.

  • OpenStack, AWS, libvirtDrivers exist in code without live verification.
  • Multi-tenant hostingWorkspaces, SSO and organization roles.
  • MCP OAuth 2.1And third-party tool-supply-chain defense.
  • Multi-agent red versus blueIncluding defender detection scoring.

Benchmarks are not discovery

Public and synthetic challenges calibrate an agent; they do not prove it can find unknown vulnerabilities.

Root-equivalent host access

The orchestrator and worker mount the Docker socket. Run Nidavellir on a dedicated host or VM, for trusted operators and authorized targets only.
